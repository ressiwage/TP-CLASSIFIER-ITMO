# ML/LLM-подход

## Какие задачи есть в системе

1. **Оценка критичности тикета** (0–5) — определяет, эскалировать ли на оператора немедленно.
2. **Поиск похожих обращений / фрагментов базы знаний** — определяет, типовой ли это вопрос.
3. **Генерация ответа для нетиповых случаев** — черновик для оператора или (в риск-контролируемых категориях) прямой ответ пользователю.

Все три задачи используют один и тот же embedding-вызов на вход (текст тикета эмбеддится один раз и переиспользуется), что важно для hot path (<500мс).

## Что решается правилами, а не ML

- Hard-triggers по ключевым словам/regex для однозначно критичных паттернов (угрозы, явный fraud, упоминания самоповреждения, оскорбления в адрес сервиса) — если сработали, критичность максимальная гарантированно, без участия модели. Semantic similarity на редких/нетипичных формулировках может промахнуться, а для таких категорий цена ошибки высокая, поэтому детерминированный слой идёт поверх ML, не вместо него.
- Роутинг по каналу обращения (chat/email/форма/приложение) — это метаданные, не требует ML.
- Базовая нормализация текста (опечатки, регистр, markdown-мусор из форм) — препроцессинг, не модель.

## Где нужна классическая ML-модель / embeddings

**Оценка критичности** — few-shot классификация через эмбеддинги: cosine similarity к центроидам категорий (baseline), либо kNN на исходных векторах, если центроиды плохо разделяют категории (пока не проверено на реальных данных). Выбран этот подход, а не обучаемый классификатор, по трём причинам:
- работает с малым количеством размеченных примеров на категорию (в PoC — десятки);
- не требует retraining при добавлении новых примеров — просто добавляется вектор;
- легко объяснить решение ("похоже на тикеты X, Y, Z с similarity 0.81"), что важно для аудита автоматических решений.

Модель эмбеддингов: `cointegrated/rubert-tiny2` — компактная (312-мерные векторы), быстрая на CPU, хорошо работает на русском тексте, не требует GPU в инференсе. Взята готовая, без дообучения — для объёма и сроков PoC дообучение неоправданно.

**Поиск похожих вопросов (retrieval)** — та же модель эмбеддингов, cosine similarity к базе вопрос-ответ. Два порога:
- широкий поиск (`R`, top-K=5, порог ниже) — определяет, есть ли вообще релевантный контекст;
- строгий поиск (`R1`, порог 0.9) — определяет, достаточно ли похоже, чтобы отдать готовый ответ без генерации.

## Где нужен LLM

Генерация ответа для случаев, которые прошли фильтр критичности, но не оказались достаточно похожи на готовый ответ из базы (`R1` пуст, `R` не пуст). LLM получает на вход top-K найденных пар вопрос-ответ как контекст (RAG) и генерирует связный ответ, а не выбирает шаблон дословно. В PoC вызов LLM — заглушка: система формирует и логирует промпт, реальный API не вызывается.

## Где LLM использовать не стоит

- Классификация критичности и поиск в hot path — LLM слишком медленный (не укладывается в 500мс) и избыточно дорогой для задачи, которую решает cosine similarity.
- Типовые/повторяющиеся обращения (`R1` не пуст) — ответ уже есть в базе знаний, генерация добавляет риск галлюцинации и стоимость без выгоды.
- Финальное решение об автозакрытии рискованных категорий — LLM не должен сам решать, что тикет безопасен; это решает классификатор критичности до LLM.

## Какие baseline запустить первыми

1. Regex/keyword hard-triggers — нулевая стоимость внедрения, ловит очевидные случаи сразу.
2. Cosine similarity к центроидам (текущий PoC) — минимальный ML-baseline, не требует обучения.
3. Следующая итерация (не в PoC): kNN вместо центроидов, если на реальных данных центроиды покажут плохое разделение категорий — центроид "размазывается", если примеры внутри категории семантически разнородные.
4. Ещё дальше: CatBoost на эмбеддингах + метаданных (канал, время суток, история пользователя) с ordinal-loss — критичность порядковая (0–5), это даст модели больше сигнала, чем чистая cosine similarity, которая не различает "далеко" и "чуть-чуть далеко". Оправдано только когда появится историческая разметка на тысячи примеров — на текущем объёме данных (десятки строк на класс) переобучится.

## Откуда берутся данные и модели

- Модель эмбеддингов — открытая (`cointegrated/rubert-tiny2`, HuggingFace), внутри не обучается.
- Данные для центроидов критичности (`criticity.txt`) и базы знаний (`questions.txt`) — в PoC это mock-датасет, написанный вручную (частично при помощи AI, см. AI_USAGE.md), не исторические тикеты.
- В целевой системе данные для базы знаний и калибровки порогов должны быть размечены на реальных исторических тикетах: нужна разметка по (а) категории критичности 0–5, (б) привязке к существующим FAQ-ответам, где применимо. Разметка — ручная выборка + возможна предразметка LLM с последующей проверкой человеком для ускорения (но не как единственный источник правды для критичных категорий).

## Технические метрики для выбора порогов и оценки качества

- Для классификатора критичности: precision/recall по каждому классу критичности (особенно важен recall на высоких категориях — пропуск критичного тикета дороже ложной эскалации), margin между top-1 и top-2 similarity как индикатор confidence.
- Для retrieval: precision@1 на hold-out наборе "вопрос → ожидаемый FAQ-ответ" — доля случаев, когда top-1 результат действительно релевантен.
- Пороги (`threshold=0.9` для строгого поиска, `margin_threshold=0.05` для confidence) в PoC заданы эмпирически ("на глаз") и требуют калибровки на размеченном hold-out наборе перед пилотом — это явное ограничение, не готовое решение.

## Обработка низкой уверенности

Два независимых сигнала неопределённости, оба ведут к эскалации на оператора, а не к попытке "угадать":
- низкий margin между top-1 и top-2 категорией критичности (`confidence="low"`);
- пустой результат retrieval (`len(R)==0`) — система не нашла ничего похожего, значит нет основания ни для готового ответа, ни для качественного RAG-контекста.

Отдельно: категория критичности выше порога `T` эскалируется независимо от confidence — то есть высокая уверенность модели в том, что тикет критичный, не отменяет участие человека, это осознанное решение в пользу безопасности, а не оптимизации автоматизации.
