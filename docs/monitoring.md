# Мониторинг в эксплуатации

## Технические метрики

- **Latency hot path** (классификация критичности + retrieval) — p50/p95/p99, ориентир до 500мс. Разбивать на этапы отдельно: время эмбеддинга, время similarity-поиска — чтобы понимать, что именно деградирует при росте нагрузки.
- **Latency генерации LLM-ответа** — отдельно от hot path, SLA мягче, но тоже нужен p95 для понимания асинхронной очереди.
- **Throughput / queue depth** — размер очереди на генерацию, особенно во время всплесков (10–20k тикетов/10мин); резкий рост очереди — сигнал включать деградацию (см. ниже).
- **Error rate по внешним вызовам** — доля неудачных вызовов LLM API (таймауты, 5xx, rate limit).
- **Доля тикетов по каждой ветке решения**: `send_to_operator` / `reply_static` / `reply_llm` — резкий сдвиг этого распределения сам по себе алертирующий сигнал (см. "деградация vs изменение потока").

## ML-метрики

- **Распределение категорий критичности** во времени (доля тикетов по каждой категории 0–5) — базовая линия для сравнения.
- **Margin confidence классификатора** (top-1 minus top-2 similarity) — средний и p10 по времени; падение среднего margin означает, что входящие тикеты становятся менее похожи на seed-примеры, т.е. модель работает "в среднем менее уверенно".
- **Recall@escalation на выборке ручной проверки**: периодически (например, раз в день) случайная выборка N тикетов из категории `send_to_operator` и N из автоматических веток проверяется вручную — считается, сколько реально критичных тикетов система пропустила в автоматику (false negative для эскалации — самая дорогая ошибка).
- **Precision@1 retrieval** — на том же выборочном ревью: для `reply_static` — действительно ли отданный ответ релевантен вопросу; для `reply_llm` — релевантен ли использованный контекст (`R`).
- **Reopen rate по каждой ветке отдельно** (`reply_static` vs `reply_llm` vs ответ оператора) — если reopen rate на автоматических ветках заметно выше, чем у оператора, это прямой сигнал занижать автоматизацию для соответствующей категории.

## Продуктовые/бизнес-метрики

(см. product.md — North Star и guardrails там; здесь просто перечисление, что именно мерится в мониторинге)

- Доля тикетов, закрытых без оператора (`reply_static` + `reply_llm` без последующей эскалации).
- CSAT в разбивке по ветке обработки.
- Reopen rate (агрегированный и по ветке).
- SLA breach rate — доля тикетов, не получивших первый ответ за 15 минут.

## Стартовые алерты

- p95 latency hot path > 500мс дольше 5 минут подряд.
- Error rate LLM API > 5% за скользящее окно 10 минут → триггерит fallback-режим (см. risks-and-ops.md).
- Очередь на генерацию растёт быстрее, чем разбирается, дольше 10 минут — риск нарушения SLA.
- Доля `send_to_operator` резко выросла (например, x2 к базовой линии за час) — либо инцидент во входящем потоке, либо деградация классификатора; требует ручного разбора, какой из двух случаев (см. ниже).
- Средний margin confidence классификатора упал ниже порога — ранний сигнал, что входящие тикеты не похожи на seed-данные, до того как это проявится в бизнес-метриках.
- Дневная стоимость LLM-инференса превысила заданный бюджетный порог (см. ниже).

## Как отличить деградацию модели от изменения входящего потока

Оба случая дают одинаковый симптом — рост `send_to_operator` и/или падение confidence — поэтому нужен разбор по двум сигналам одновременно:

- **Изменение потока (не поломка модели)**: рост объёма тикетов резко коррелирует по времени с внешним событием (алерт от мониторинга самого сервиса, инцидент, релиз) — конкретная новая тема/кластер тикетов, которого раньше не было, если посмотреть на кластеризацию текстов за последний час. Обычно затрагивает одну-две категории, а не всё распределение сразу.
- **Деградация модели**: confidence падает равномерно по всем категориям без привязки к внешнему инциденту, либо метрика точности на выборочном ручном ревью падает при стабильном по составу потоке. Также стоит проверять на конкретных regression-примерах (эталонный набор из 20-30 тикетов с известной правильной категорией, прогоняется на каждый релиз/обновление данных).

На практике: при подозрении на инцидент во входящем потоке — первым делом смотреть на кластеризацию свежих тикетов (похожи ли новые тикеты друг на друга сильнее, чем на исторические), а не сразу считать, что модель сломалась.

## Мониторинг стоимости LLM

- Стоимость считается по количеству вызовов `reply_llm` × средняя цена вызова (входные токены = промпт с RAG-контекстом, довольно предсказуемый размер) — трекается по дням и по неделям.
- Отдельно мерится **доля тикетов, доходящих до LLM-генерации** от общего потока — рост этой доли при стабильном общем объёме тикетов означает, что retrieval (`R1`, строгий порог 0.9) стал реже находить точное совпадение — сигнал либо пересчитать базу знаний, либо разобраться, не сместился ли поток.
- Бюджетный порог в день/неделю задаётся заранее (assumption, не дано в задаче) — при приближении к порогу алерт, при превышении — рассмотреть временное ужесточение порога `R1` (больше тикетов уходит на `reply_static`/эскалацию, меньше — на дорогую генерацию) как контролируемую деградацию по стоимости, а не по надёжности.

## Как отслеживается, что решается реальная исходная задача

Технические и ML-метрики могут быть в норме, а система при этом не приносить пользы (например, если операторы всё равно перепроверяют вручную все автоматические ответы, или CSAT падает при формально хорошем precision). Поэтому отдельно от технических дашбордов:
- еженедельный ручной аудит случайной выборки автоматических решений (`reply_static` и `reply_llm`) с фокусом не на "похож ли текст", а на "решил ли ответ проблему пользователя" — метрика ближе к продуктовой, чем к технической;
- сопоставление тренда North Star метрики (доля закрытых без оператора) с трендом CSAT и reopen rate в одном дашборде — рост автоматизации при одновременном падении CSAT/росте reopen считается провалом, даже если все ML-метрики выше порога;
- отдельная проверка на регресс по самой дорогой ошибке — пропущенная эскалация критичного тикета — не по метрике, а по реальным инцидентам/жалобам, дошедшим до эскалации вручную post-factum.
